# dsh-auto-research 架构重构：monorepo、LayerFS 原生分支、会话续接、Colab CLI 执行

- 日期：2026-11-03
- 状态：已实施；与本文不同的地方见 §11
- 基准：`feat/layerfs-1.1` @ `f8ad998`
- 前一版：[design-2026-11-02.zh.md](design-2026-11-02.zh.md)。本文取代其中 D4、D9、D10、D11、§4.1 的 `FrozenEvaluator` 职责划分、§4.4 dsh-colab 迁移；其余决策（计划校验前置、停滞计时跨批次、提示词 skill 化、注册表与优先级）保持有效。
- 对照：原版 ara（`rohanarun/Auto-research-agent`，`Resources/ResearchMethods.py`）

## 0. 为什么重构

现有代码是在"工作区是宿主机目录、worker 可能乱改文件、评估器在本机跑"的前提下写的，所以有大量防御：冻结评估器副本、评估前后比对清单、宿主机暂存层、snapshot 回退、handoff 文件。三个前提已经变了：

1. **LayerFS 隔离**：每个分支是 LayerFS branch，挂在 Sandbox 里，worker 只能改自己的分支；提交就是检查点。宿主机上不再需要分支目录。
2. **续接用原生会话**：continue 阶段应续接 leader 自己的 worker 会话，而不是新建 worker 再读 handoff 文件。
3. **GPU 都在云端**：评估和 worker 的 GPU 试验都在 Colab 上跑，本机只负责调度。

本文定义重构后的分层、包结构、接口、批次流程、删除清单和实施顺序。

## 1. 决策摘要

| # | 决策 |
|---|---|
| A1 | pnpm monorepo：一个目录一个包，一个包一个 Cordis 插件，按目录分组（与 dsh `packages/<group>/<pkg>` 相同） |
| A2 | 六层：Coordinator、Runner、Workspace、Worker、Evaluator、Executor；只有 Workspace 和 Executor 是可替换的插件 |
| A3 | Workspace 只有 LayerFS 一个实现；删除 snapshot 后端和宿主机暂存层；分支状态用 `{ branch, commit }` 表示 |
| A4 | explore 新建 worker；continue 在 leader 的分支上续接 leader 自己的会话（同一 childId），不新建 worker，不写 handoff |
| A5 | Evaluator 是协调者为每个任务写的纯打分脚本；核心只记录它的 SHA-256，不冻结副本、不比对清单、不校验证据 |
| A6 | Executor 的输入是 LayerFS 引用加命令；排队、隔离、超时都归 Executor；Colab 实现直接调用 Colab CLI |
| A7 | worker 的 CPU 执行在 LayerFS Sandbox 内（`workspace exec`）；GPU 试验通过核心提供的工具交给 Executor，与评估共用一条路径 |
| A8 | 默认值与 ara 对齐：`rounds: 3`、`branches: 4`、explore 5 分钟、continue 15 分钟 |
| A9 | 旧测试随被删代码一起删除；验收是在 LayerFS 上实际跑通一个 demo 批次 |

## 2. 六层职责

| 层 | 职责 | 形式 |
|---|---|---|
| Coordinator | 理解任务，写 plan（目标、worker 提示词、指标、选项）和 evaluator 脚本，调用 `subagent_auto_research` | dsh 主会话 + 协调者 skill |
| Runner | 调度：建基线、fork、启动和续接 worker、提交、调用评估、选 leader、停滞判定、写 trajectory 和 `LATEST.json` | 核心包，唯一实现 |
| Workspace | 分支的创建、挂载、提交、释放 | 插件：`workspace-layerfs` |
| Worker | 在自己的分支里做研究 | dsh `ctx.subagents` 的进程内 provider（`spawn`） |
| Evaluator | 读分支内容，输出一行 JSON 分数 | 任务数据：plan 里的脚本路径 |
| Executor | 在某个计算环境里，对某个分支的某次提交运行一条命令 | 插件：`executor-local`、`executor-colab` |

判断是否做成插件的标准：同一层有多个真实实现，或实现依赖特定环境。Worker 的可替换性已经由 dsh 的 subagent provider 提供，不需要再包一层。

## 3. 包结构（A1）

```

packages/
  core/
    api/                → dsh-auto-research-api                  接口与公共类型；不注册任何东西
    auto-research/      → dsh-auto-research                      Runner、SubagentProvider、skills、注册表、cordis.patch.yml
  workspace/
    workspace-layerfs/  → dsh-auto-research-workspace-layerfs    LayerFS 后端（运行时动态加载 LayerFS SDK）
  executor/
    executor-local/     → dsh-auto-research-executor-local       在 LayerFS Sandbox 内运行（CPU）
    executor-colab/     → dsh-auto-research-executor-colab       调用 Colab CLI（GPU）
tests/                    e2e，留在根目录

```

| 包 | Cordis 名称 | inject |
|---|---|---|
| `dsh-auto-research` | `dsh-auto-research` | `subagents`、`skills` |
| `dsh-auto-research-workspace-layerfs` | 同包名 | `researchWorkspace` |
| `dsh-auto-research-executor-local` | 同包名 | `researchExecutor` |

依赖规则：

- 实现包只依赖 `dsh-auto-research-api`，不引用核心内部文件。
- `api` 不依赖 Cordis、不依赖 LayerFS SDK。
- 核心提供 `ctx.researchWorkspace`、`ctx.researchExecutor` 两个注册表（`registry.ts` 原样保留），实现包向注册表注册工厂。

不加 npm scope；如果以后要发布到 registry，再统一改成 `@dsh-auto-research/*`。

## 4. 接口（`dsh-auto-research-api`）

### 4.1 Workspace

```ts
/** 一个分支在某次提交时的状态。Runner 只持有这个值，不持有宿主机路径。 */
export interface BranchRef {
  readonly branch: string
  readonly commit: string
}

/** 一个已挂载、worker 可以工作的分支。 */
export interface MountedBranch {
  readonly branch: string
  /** worker 的 cwd：Sandbox 内的挂载路径。 */
  readonly path: string
  /** 后端自己的挂载句柄，Runner 不读取。 */
  readonly handle: unknown
}

export interface WorkspaceBackend {
  readonly name: string
  /** 把协调者给的源目录导入为基线分支并提交。 */
  baseline(source: string, id: string): Promise<BranchRef>
  /** 从某次提交 fork 出新分支并挂载。 */
  fork(from: BranchRef, id: string): Promise<MountedBranch>
  /** 重新挂载已有分支（continue 阶段在 leader 分支上原地继续）。 */
  mount(branch: string): Promise<MountedBranch>
  /** 提交挂载中的分支，返回新的提交。 */
  commit(mounted: MountedBranch, message: string): Promise<BranchRef>
  /** 卸载；discard 为 true 时删除分支。 */
  release(mounted: MountedBranch, options: { discard: boolean }): Promise<void>
  close?(): Promise<void>
}
```

相对现有 `WorkspaceBackend`（`src/types.ts:634`）删除的方法：`reconcile`、`adopt`、`retainCompletedState`、`restoreCompletedState`、`estimateForkBytes`。理由：

- `reconcile` 只服务于宿主机暂存层与 Sandbox 双写，暂存层删除后不再存在。
- `adopt` 被 `mount` 取代：上一批的 leader 就是一个分支名。
- `retain/restoreCompletedState` 用来在续接失败时恢复上一次完成的状态；LayerFS 提交本身就是检查点，失败时用上一次 `BranchRef` 即可。
- `estimateForkBytes` 和 `checkDisk`（`runner.ts:611`）：LayerFS fork 是写时复制，不需要预估磁盘。

### 4.2 Executor

```ts
export interface ExecutionRequest {
  /** 要运行的代码：某个分支的某次提交。 */
  readonly ref: BranchRef
  /** 额外放进执行环境的文件，例如 evaluator 脚本；不进分支。 */
  readonly files?: ReadonlyArray<{ readonly name: string; readonly text: string }>
  /** 在分支根目录下执行的命令。 */
  readonly argv: readonly string[]
  readonly timeoutMs: number
  readonly signal?: AbortSignal
}

export interface ExecutionResult {
  readonly code: number | null
  readonly timedOut: boolean
  readonly stdout: string
  readonly stderr: string
  /** 执行环境的标识，例如 `local`、`colab:H100`；写入 trajectory。 */
  readonly environment: string
}

export interface ExecutorBackend {
  readonly name: string
  run(request: ExecutionRequest): Promise<ExecutionResult>
  close?(): Promise<void>
}
```

Executor 自己负责：

- **排队**：同一个执行环境同一时刻只跑一个请求时，由 Executor 串行化，不交给调用方。
- **隔离**：每个请求一个独立工作目录，从 `ref` 取代码，不复用上一个请求的文件。
- **超时**：到 `timeoutMs` 时真正停止进程，而不只是不再等待。

### 4.3 Evaluator

不是接口，是 plan 里的两个字段：

```jsonc
{
  "evaluator": "/abs/path/evaluate.py",   // 协调者写的脚本，在分支之外
  "evaluator_interpreter": ["python3"]    // 可选
}
```

约定：脚本以分支根目录为当前目录运行，最后一行输出 JSON：`{ "valid": true, "score": 1.23, "metrics": { ... } }`。

Runner 在批次开始时读取脚本文本并计算 SHA-256，之后每次评估都把同一份文本通过 `ExecutionRequest.files` 传给 Executor。worker 改不到这份文本：它在分支之外，worker 只能写自己的分支。

## 5. 一个批次的流程

```
AutoResearchProvider.start(request)
 ① preparePlan                          校验 plan，读取 evaluator 文本并计算 sha256
 ② workspaces.select / executors.select 按 options.workspaceBackend、options.executor 选择插件
 ③ 基线
    ├ 有 LATEST.json 且 evaluator sha256 相同 → 用其中的 leader BranchRef 作为基线
    └ 否则 → workspace.baseline(plan.workspace)，evaluate(基线)
 ④ for round in 1..rounds
    ├ explore（停滞时进入；首轮按 rsiTop 规则）
    │  ├ 对 i in 1..branches 并行：
    │  │  ├ workspace.fork(leader.ref, id)               → MountedBranch
    │  │  ├ subagents.startActivation({ provider: 'spawn', childId, request: { cwd: mounted.path, prompt, parent }, delivery: 'caller' })
    │  │  ├ 到 explorationMinutes 时 interrupt；await activation.result
    │  │  ├ workspace.commit(mounted)                     → BranchRef
    │  │  └ evaluate(BranchRef)
    │  └ choose()                                        选出新 leader，记录它的 childId
    ├ continue
    │  ├ workspace.mount(leader.branch)
    │  ├ continueWorker(leader.childId, 续接消息)          见 §6
    │  ├ 到 exploitationMinutes 时 interrupt；等待这一轮结束
    │  ├ workspace.commit → evaluate
    │  └ 更新停滞计时（meaningful_gain、stall_seconds）
    └ 释放非 leader 分支（forkAndFlush 规则不变）
 ⑤ 写 trajectory、LATEST.json（frontier 以 evaluator sha256 + executor 名称为键）
 ⑥ 返回 leader 的 BranchRef 和分数给协调者

evaluate(ref)
 ① executor.run({ ref, files: [{ name: '.auto-research/evaluate.py', text }], argv: [...interpreter, '.auto-research/evaluate.py'], timeoutMs: evaluation_seconds * 1000 })
 ② 取 stdout 最后一行 JSON；解析失败或 code ≠ 0 → { valid: false, reason }
 ③ 记录 { score, metrics, environment, evaluator_sha256 }
```

保持不变的算法：`rsiTop`（随机指标视图 + `PORTFOLIO.json`）、`forkAndFlush`、`choose()`、停滞判定、协作模式的 epoch 划分。它们只改数据来源（`BranchRef` 代替宿主机目录），不改语义。

## 6. continue 续接 leader 的会话（A4）

### 6.1 dsh 现有能力

- `ctx.subagents.startActivation` 对实现了 `prepareContinuable` 的 provider 走 `manager.startLocal`，创建可续接的进程内子 agent，描述符 `mode: 'continuable'`。目前实现它的是 `subagent-spawn-in-process` 和 `subagent-fork-in-process`。
- `claude-code`、`codex` 等外部 provider 走 `startExternal`，不能续接（`NOT_CONTINUABLE`）。
- 续接入口是 `sendMessage` / `steerPrompt` / `queuePrompt`，都进入 `deliverToChild`：子 agent 常驻则直接投递，否则 `coldResume`，从持久化的会话事件恢复（需要 `sessionPersistence`）。
- 本地 activation 在第一轮自然结束时关闭；`activation.result` 只对应第一轮。

### 6.2 缺口

这几个入口都只返回 `messageId`，调用方拿不到"续接这一轮何时结束、结果是什么"；冷恢复的子 agent 结束时会向父会话（协调者）发 `subagent-settled` 消息。Runner 需要的是和 `startActivation` 一样的 `SubagentActivation`：能 await 结果、能 dispose、不通知父会话。

### 6.3 方案：在 dsh 增加 `continueActivation`（已被 §11 的种子方案取代）

```ts
// ctx.subagents
continueActivation(spec: {
  readonly parent: Agent
  readonly childId: SessionId
  readonly content: ContentBlock[]
  readonly signal: AbortSignal
  readonly delivery: 'caller'
}): Promise<SubagentActivation>
```

实现复用 `manager.coldResume` 已有的恢复路径，区别只在于：返回 activation 本身（含 `result`），且 `delivery: 'caller'` 时不向父会话发 `subagent-settled`。这是对 deepseek-harness 的一个独立 PR。

Runner 侧：

```
continueWorker(childId, message)
 ① subagents.continueActivation({ parent: this.parent, childId, content: [message], delivery: 'caller' })
 ② 到期 → subagents.interrupt(childId, { kind: 'ancestor', agent: this.parent })
 ③ await activation.result
```

续接消息只说明本轮的时间预算、当前分数和评估摘要；不再写 `HANDOFF.md`、不再要求 worker 写 `RESEARCH_HANDOFF.md`。

### 6.4 外部 provider

外部 provider 的子 agent 不能续接。本次只支持进程内 provider：plan 指定了外部 provider 时，`preparePlan` 直接报错。`PREFERRED_WORKERS`（`provider.ts:63`）缩减为 `['spawn']`。如果以后需要 Claude Code / Codex worker，在 dsh 对应 provider 里实现会话恢复（Claude Agent SDK 有 `resume`，codex 有 thread resume），再放开。

## 7. Executor 实现（A6、A7）

### 7.1 `executor-local`

在 LayerFS Sandbox 内运行：

```
LocalExecutor.run(request)
 ① workspace 插件提供的 Sandbox 客户端：从 request.ref fork 一个临时分支并挂载
 ② 写入 request.files
 ③ client.workspace.exec(mount, argv)，超时到期时终止
 ④ 卸载并删除临时分支
```

本地执行不再在宿主机上跑进程，宿主机不出现分支文件。

### 7.2 `executor-colab`

直接调用已登录的 Colab CLI（`~/.local/bin/colab`，凭据在 `~/.config/colab-cli/`），不再自建队列服务器、cloudflared 隧道和连接文件。

已确认的 CLI 行为及处理：

| CLI 行为 | 处理 |
|---|---|
| 同一个 kernel 一次只执行一个请求 | 插件内每个 Colab 会话一个串行队列 |
| `exec` 默认超时 30 秒，计时包含排队时间 | 每次调用显式传超时；排队在插件内部完成，不交给 CLI |
| 超时的请求不会被中断，之后仍会执行 | 超时后调用 `restart-kernel`，再处理下一个请求 |
| 同一会话共享 kernel 状态、CUDA 上下文和 `/content` | 每个请求在 `/content/ar/<runId>/<requestId>/` 下执行，结束后删除；每个请求起一个新的 Python 进程，不在 kernel 内 import |
| 输出按 msg_id 过滤，不会混在一起 | 不需要额外处理 |

执行步骤：

```
ColabExecutor.run(request)
 ① 排队到某个会话
 ② 从 LayerFS 读取 request.ref 的文件，打包，加上 request.files，colab upload
 ③ colab exec：cd 到请求目录，subprocess 执行 argv，限时 timeoutMs
 ④ 收集 code、stdout、stderr；超时则 restart-kernel
 ⑤ 删除请求目录；environment 记为 `colab:<GPU 型号>`
```

配置：

```yaml
- id: auto-research-executor-colab
  name: 'dsh-auto-research-executor-colab'
  config:
    gpu: H100            # 新建会话时使用
    sessions: 1          # 并行会话数，即同时运行的请求数上限
    createSessions: false
```

`createSessions` 默认为 false：Colab 会话消耗计算单元，默认只使用已经存在的会话；要由插件新建会话，需要显式开启。

### 7.3 worker 的 GPU 试验

worker 在 Sandbox 里，没有 Colab CLI 和凭据。核心为 worker 提供一个工具 `research_run`：

```
research_run({ command, timeout_seconds })
 ① workspace.commit(worker 当前的分支)          → BranchRef
 ② executor.run({ ref, argv, timeoutMs })
 ③ 把 code、stdout、stderr 返回给 worker
```

worker 的试验和正式评估走同一个 Executor、同一个队列；worker 不知道也不关心后面是本地还是 Colab。CPU 上的小命令仍由 worker 直接在 Sandbox 里执行。

- 注册表与优先级选择（`registry.ts`）。
- 计划校验前置、停滞计时跨批次（前一版 D1、D2）。

## 9. 实施顺序

一次重构完成，按以下顺序提交，每步一个 commit：

1. monorepo 骨架：`pnpm-workspace.yaml`，按 §3 拆出各包，核心改为从 `dsh-auto-research-api` 引用类型。
2. Workspace：新接口；`workspace-layerfs` 删除暂存层，worker cwd 指向 Sandbox 挂载路径；删除 snapshot。
3. deepseek-harness：`ctx.subagents.continueActivation`（单独的 PR；后来改为插件内的种子方案，见 §11）。
4. Runner：`BranchRef` 状态、continue 续接会话、删除 handoff 和恢复字段、默认值改为 A8。
5. Evaluator 精简；Executor 新接口；`executor-local`。
6. `executor-colab`（Colab CLI）和 worker 工具 `research_run`。
7. skills、README、`cordis.patch.yml` 更新。
8. 验收：在 LayerFS 上跑 `ar-demo-sort` 批次（`executor-local`），确认 explore fork、continue 续接同一 childId、提交和评估都正常；Colab 验收需要先确认计算单元用量。

| V6 | `research_run` 是否需要限制每个 worker 的并发或总时长，防止一个 worker 占满 Colab 队列 | §7.3 |

## 11. 实施记录

实施时以下几处与上文不同，以本节为准。

**V1 不成立，Workspace 接口随之改变。** dsh-layerfs 的 worker 不通过 cwd 访问分支：它的 bash 在宿主机上运行，cwd 是一个草稿目录，项目通过 `layerfs` 命令按分支名访问（`DSH_LAYERFS_PROJECT` 按根会话绑定，`spawn` 子 agent 自动继承）。Sandbox 挂载路径在容器内，宿主机进程无法把它当 cwd。因此：

- Runner 不替 worker 挂载。`fork` 只创建分支，返回 `BranchRef`；worker 结束后 Runner 用 `head(branch)` 读取分支最新提交。
- worker 的 cwd 是 `runs/<run>/<branch>/scratch`，放 `BRANCH.json`、`NOTES.md`、`PORTFOLIO.json`。
- `WorkspaceBackend` 改为：`fork`、`head`、`readText`、`run`（在自己的 Sandbox 中对某个提交执行命令，卸载时丢弃改动）、`exportTree`（导出 tarball，供 Colab 使用）、`close`。没有 `mount`、`commit`、`release`。
- `ExecutionRequest` 带上 `workspace`，`executor-local` 直接调用 `workspace.run`。
- LayerFS 没有删除分支的接口，所以不再有 `release`。分支 head 已经越过要执行的提交时，`run` 和 `exportTree` 会在该提交上 fork 一个临时分支（`<branch>-at-<n>`），这类临时分支会留在项目里。

**V2 成立。** deepseek-harness 分支 `feat/subagent-continue-activation`（提交 `4fa38ccba4`）新增 `ctx.subagents.continueActivation`，复用 `coldResume` 的恢复路径。区别只有两点：返回本轮的 activation；`delivery: 'caller'` 时不向父会话发 `subagent-settled`。子 agent 仍常驻（上一轮尚未结束）时拒绝，错误码 `CHILD_RESIDENT`。

**其余变化：**

- 协作模式（`shareContext`）本次删除（V5）。
- §7.3 的 `research_run` 是 dsh 工具，参数为 `{ command, timeout_seconds }`，命令用 `bash -c` 执行。
  - 注册时带 `when({agent})` 条件：只有 runner 登记过的 worker 会话能看到它。fresh worker 用预留的 childId 启动，runner 先登记再启动，所以第一步就能看到。
  - 收到调用后，取该分支的 head，交给本批次的执行器运行。同一个 worker 的请求串行执行，超时时间不超过该回合的剩余时间。
  - 结果文本包括环境、提交、退出码，以及 stdout、stderr 各自最后 20000 个字符。
  - 第一版曾做成 CLI（本地 HTTP 接口 + 每个会话一个 token，经 `ctx.shellEnv` 注入三个环境变量），已删除。
- `executor-colab` 不新建会话，除非配置了 `createSessions`；默认只使用配置里列出的会话。
- 前沿不匹配（评估器或执行器变了）时，基线不是 `plan.base`，而是 fork 上一批的 leader 并用新评估器重新打分，停滞计时清零。
- 后续清理（去掉防御性校验）：
  - 删除 evaluator sha256 和 frontier。每个批次开始都用本批的评估器和执行器重新给起点打分；`LATEST.json` 只保存 leader 和停滞计时。上一条随之作废。
  - 删除 runner 锁、worker 发起批次的拦截、worker provider 能否续接的检查、worker 模型名匹配、起点必须有效的检查。
  - plan 只要求 objective、worker_prompt、evaluator、evaluation_seconds，其余字段给默认值，不再校验 metrics、selection_metrics 和 RSI-top 参数。
  - 评估器输出只要求 `valid: true` 时 score 是数字，不再逐个检查声明过的 metrics。
- `executor-colab` 改走 ssh：§7.2 的 `colab upload` + `colab exec` 方案作废。
  - 实测 `colab exec` 一次空命令要 30 秒左右；而且 CLI 在 websocket 连上之前就发出 execute_request，请求会丢，CLI 一直等到自己的超时，kernel 却是空闲的。
  - 现在每次请求：`ssh -o ProxyCommand="colab ssh --proxy-mode -s <会话>"`，提交的 tar 包从 stdin 传入，远端解包、`timeout -k 10` 执行、删除目录。连接用 ControlMaster 复用：首次约 3 秒，之后约 1 秒。
  - ssh 密钥自动生成在 `~/.cache/dsh-auto-research/ssh/id_ed25519`，不碰 `~/.ssh`。
  - `restart-kernel`、`run.py`、结果标记行全部删除。
- 包结构再调整（A1、A2 的修订）：按「每个部分一个插件」划分，提示词也单独成包。
  - `workspace-layerfs` 承担全部 LayerFS 代码：直接提供 `ctx.researchWorkspace` 服务（只有一个实现，不再用注册表和工厂），自己通过 `ctx.shellEnv` 读取协调者的 `DSH_LAYERFS_*`，并把自己的 Sandbox 登记为 `sandbox` 执行器。核心里不再有 LayerFS 和环境变量相关的代码。
  - `executor-local` 删除（它只是一行转发），由上面的 `sandbox` 执行器取代。
  - 协调者 skill 和 worker 说明分别成为只含提示词的包 `dsh-auto-research-coordinator`、`dsh-auto-research-worker`。
    - 协调者那份仍是 skill（注册函数放在 `api` 里共用），所有会话可见。
    - worker 那份不再是 skill，而是 `worker.md`，用 `ctx.systemPrompt.context` 注入：文字函数在每次组装 prompt 时判断 `ctx.researchWorkers.has(agent.id)`，只有正在运行的 worker 拿到全文，其他会话为空字符串。runner 先登记会话再启动或续接 worker，所以第一步就有。worker 的 prompt 不再要求加载 skill。
    - worker 不再有 `subagent_auto_research` 工具：核心监听 `agent/created`，会话在 `ctx.researchWorkers` 里时，用 `agent.ctx.tools.restrict({ deny: ['subagent_auto_research'] })` 拿掉它（新建和续接的 worker 都会触发）。`worker.md` 里「不要调用」那条规则删除。
  - 核心里的三套 worker 表（`Runner.live`、`ActiveWorkers`、`WorkerRuns`）合并为一个 `Workers`。
  - portfolio 只记录：读不到或格式不对时写入 `portfolio_error`，不拦 `research_run`，也不作废分数；这份数据不参与任何选择。
  - 删除未使用的 `readText`、`runId`、`BackendCreateOptions`。
- 续接不再改 dsh（取代 §6.3 和 V2 的 `continueActivation`）。核心多注册一个 provider `auto-research-continue`，只实现 `prepareContinuable`：
  ① runner 预留新的会话 id，用 `ctx.sessionQuery.observeSession(leader 会话)` 读出旧 worker 的事件，截到最后一个 `turn/end`，记在这个 id 下。
  ② `startActivation({ provider: 'auto-research-continue', childId: 新 id, prompt: 续接消息, delivery: 'caller' })`。dsh 创建子会话时调用 `prepareContinuable`，拿到这段事件作为种子，和 fork provider 用父会话做种子是同一条路。
  ③ 新会话带着旧 worker 的完整历史开始这一轮，结果和 explore worker 一样从 `activation.result` 拿到，不通知协调者。
  - 每次续接都是新的会话 id；`Workers`、`research_run`、`worker.md` 注入、去掉批次工具都按新 id 生效。
  - 种子不检查父子关系，所以换了协调者会话也能续接。读不到旧会话（没有持久化、会话已删）时，continue 阶段退回到 fork 加新 worker。
- 按一次评审修正（e46d490 之后）：
  - continue 不再改 leader 的分支：每次 continue 从 leader 的提交 fork 新分支，目录建在本批次下并先复制 leader 的目录。一个分支在它的回合结束后不再改动，`TrajectoryRow` 的分支、提交、会话、目录一一对应；上一批的运行目录也不再被写入。
  - `Workspace` 接口去掉 `run`，只管分支和导出；在 Sandbox 里执行由 `sandbox` 执行器负责，和 Colab 一样一次只跑一个命令。
  - 调用方中止（worker 到时被打断、批次停止）时只是不再等待；执行器的队列等命令真正结束才放行下一个请求，评估不会和残留的 `research_run` 同时运行。`research_run` 的超时本来就不超过 worker 剩余时间，所以残留命令在截止后约 10 秒内结束。
