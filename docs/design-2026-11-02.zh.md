# dsh-auto-research 重设计：P0 修复、skill 化提示词、插件化后端

- 日期：2026-11-02
- 状态：草案，未实施
- 基准：`main` @ `3702bac`
- 对照：原版 Auto Research 应用（本机 `~/DimReview/ara`，远端 `rohanarun/Auto-research-agent`），`src/runner.ts` 移植自其 `Resources/ResearchMethods.py`
- 语言：目前只有中文版，英文版待定稿后补齐

## 0. 背景与范围

本仓库是原版 macOS 应用的 dsh 重写。重写不追求与原版逐行对齐：原版只用来区分"原版就有的设计"和"移植时引入的问题"，取舍以 dsh 的结构为准——一个 `SubagentProvider`、协调者一次委派一批、LayerFS 为主力工作区后端。

本文覆盖四件事：

1. P0：四个会导致错误行为的问题。
2. 提示词全部改为 skill，删除常驻 systemPrompt 段落。
3. 工作区后端与执行后端拆成"核心定义接口、插件提供实现"，Colab 是执行后端的一个插件。
4. LayerFS 成为主力后端后需要的接口调整，以及其余收敛项。
5. 删减过度防御的代码：校验只留在不可信输入上。

不在范围内：评估器的科学正确性、RSI-top / fork-and-flush 的算法本身、`choose` 的排序语义（见 §6.5）。

## 2. P0：行为修复

### 2.1 计划校验前置（D1）

现状：`validatePlan` 在 `new Runner` 内执行（`runner.ts:443-444`），此时已经加锁、建了 `runs/<runId>/`、写了 `SEED.json`、可能已挂载上一批的 LayerFS 分支（`provider.ts:1241-1359`）。缺 `worker_prompt`、`branches < 2` 等错误会留下目录和挂载。原版在 `run()` 开头先校验再建目录（`ResearchMethods.py:516-534`），这是移植时引入的问题。

改后的 `start()`：

```
AutoResearchProvider.start
 ① preparePlan(cwd, config)
     ├ resolvePlan                      读 config.plan 或 planPath（PR6 起只有这两处）
     ├ 规范化 evaluator 绝对路径并 stat
     ├ normalizeOptions
     └ validatePlan                     → { plan: ResearchPlan, options: ResearchOptions }
 ② workerProviderName / resolveLiveWorkerAgentOptions
 ③ selectPlanWorkspace                （PR6 删除 assertRuntimeRootContained）
 ④ acquireRunnerLock
 ⑤ mkdir runs/<runId>，写 SEED.json
 ⑥ workspaces.select → new WorkspaceManager → adopt
 ⑦ new Runner({ plan, options, ... })   不再重复校验
```

`Runner` 构造函数仍调用 `validatePlan`：它是纯函数、可重复执行，测试和独立使用会直接构造 `Runner`。provider 侧的提前校验保证了无效计划不留任何状态。测试：计划无效时 `runs/` 下无新目录、无 `runner.lock`、后端 `baseline/adopt` 未被调用。

### 2.2 停滞计时跨批次（D2）

现状：`bestTime` 在基线评估后重置（`runner.ts:843`），停滞判定只看本批内的墙钟（`:848-852`）。原版默认 `rounds=3`，前几轮的 continue 可以累计到 `stall_seconds`；本仓库默认 `rounds=1`，所以单开 RSI-top 永远不进入探索阶段。

不恢复 `rounds=3`。dsh 的用法是协调者一批一批地委派，停滞状态应跨批次保存。`LATEST.json` 新增：

```json
{
  "leader_workspace": "…",
  "leader_branch": "…",
  "original_manifest": { "…": "…" },
  "frontier": {
    "evaluator_sha256": "…",
    "anchor_score": "0.8125",
    "stalled_work_seconds": 840
  }
}
```

规则：

```
Runner.runBatch
 ① 读取 frontier；evaluator_sha256 与本批冻结哈希不同 → 丢弃 frontier
 ② 基线评估；无 frontier 时 anchor = 基线分数，stalled_work_seconds = 0
 ③ 每轮开始：stalled = rsiTop && stalled_work_seconds >= stall_seconds
 ④ 每个阶段结束：
     gain > meaningful_gain → anchor = 当前分数，stalled_work_seconds = 0
     否则                  → stalled_work_seconds += 本阶段耗时（阶段开始到选择完成）
 ⑤ writeSelection 写回 frontier
```

只计阶段耗时，不计墙钟。协调者在两批之间停多久都不会被判为停滞。`anchor_score` 以字符串保存，避免浮点往返误差。

已知性质：恢复 frontier 时，本批的基线分数不覆盖 `anchor_score`。评估器有噪声时，第一个阶段可能因为重新评估偏高而被记为提升，从而清零停滞计时。这是有意的：anchor 表示历史上记录过的最好分数。

### 2.3 默认值（D3）

现状：`resolveConfig` 默认 `rsiTop=false, forkAndFlush=false`；`cordis.patch.yml` 两者都为 `true`；README 安装示例为 `rsiTop: true, forkAndFlush: false`。三处互相矛盾，且安装示例这一组合加上 `rounds: 1` 只会跑 1 个分支。

决定：

- 代码默认值保持全关。`rsiTop=true` 会要求每个计划都带 `stall_seconds`、`metric_subset`、`portfolio_size` 和正的 `meaningful_gain`，不适合作为代码默认值。
- `cordis.patch.yml` 是推荐配置，保持 `rsiTop: true, forkAndFlush: true`。
- README 配置表写代码默认值；安装示例逐字复制 `cordis.patch.yml`。
- `tests/package.test.ts` 增加断言：README 两个语言版本中的安装示例与 `cordis.patch.yml` 的配置字段一致。

### 2.4 续跑机制定为 handoff（D4）

现状：`startActivation` 不能恢复会话，runner 也没有传 session（`runner.ts:1264`）。但：

- `LAUNCH.json` 写 `fresh_context: !session`，continue 分支会被记成 `false`，与事实不符。
- 协作 cohort 把 `!row.provider_session` 当作未完成（`runner.ts:1035`）。worker provider 不返回 `childId` 时，每个 cohort 跑完第 1 个 epoch 就结束。

决定：

- 续跑的正式机制是 handoff：上一轮的 `last_output` 写入 `.auto-research-methods/HANDOFF.md`，加上 worker 自己维护的 `RESEARCH_HANDOFF.md`。现有位置 `.auto-research-methods-handoff.md`（`runner.ts:1175`）不在 `OMIT` 中（`OMIT` 按完整名称匹配），会进入清单、参与评估、被 fork 进子分支，因此移入 `.auto-research-methods/`。
- `LAUNCH.json` 删除 `fresh_context`，新增 `continuation`：写了 handoff 时为 `"handoff"`，全新分支为 `"none"`；`provider_session` 照常记录。
- 协作完成判定只看 `completed`、`evaluation.valid` 与 `collaboration_failed`。
- 宿主以后若提供 `capabilities.resume`，再增加 `continuation: "session"`，不在本次范围。

## 3. 提示词全部改为 skill（D5、D6）

### 3.1 现状

`coordinatorPolicy()`（`policies.ts:38`）把原版的 `ResearchPolicy.md`、`ResearchMethodsPolicy.md`、`ContinuePolicy.md` 原样拼接，再加一段 dsh addendum，合计约 27.7KB，在每个会话常驻注入。前文描述的是 macOS 应用（外置 SSD、Daytona、`ResearchMethods.py`、`RESEARCH_METHOD_PLAN: ready`、Lean/QRH、官方评测），addendum 声明"覆盖前文"。冲突点：

- 前文要求"不要在自己的工具调用里启动 runner"，addendum 要求调用 `subagent_auto_research`。
- 前文称 continue 与协作 epoch 会恢复 provider 会话，实际不会（§2.4）。
- 前文要求输出 `RESEARCH_STATUS` 行，没有代码解析它。

### 3.2 skill 清单

| skill | 读者 | 提供方 | 内容 |
|---|---|---|---|
| `auto-research` | 协调者 | 核心 | 何时使用；计划 schema；评估器契约；RSI-top / fork-and-flush / 协作的语义；批次结束后的审阅清单 |
| `auto-research-worker` | 分支 worker | 核心 | 分支内的工作方式；`BRANCH.json` 的读法；`PORTFOLIO.json`、`SHARED_CHECKPOINT.json`、`PEER-REVIEW.json` 的格式；禁止递归委派与发布 |
| `auto-research-layerfs` | worker | layerfs 插件 | Sandbox 路径与宿主 checkout 的关系；单写入方规则（§5.2） |
| `auto-research-colab` | 协调者、worker | colab 插件 | 计划里如何选用 colab 执行后端；worker 如何通过 `$DSH_COLAB_CLI` 提交 GPU 任务 |

每个 skill 是包内的 `skills/<name>/SKILL.md`，frontmatter 带 `name` 与 `description`。`auto-research-worker` 设 `user-invocable: false`。全部内容按 dsh 的实际流程重写，不再引用原版应用。`policies.ts` 中的 `RESEARCH_POLICY`、`RESEARCH_METHODS_POLICY`、`CONTINUE_POLICY`、`SHARED_CONTEXT_POLICY`、`DSH_COORDINATOR_ADDENDUM` 删除。

### 3.3 协调者：通过 `ctx.skills` 注册

写法与 dsh 的 `skill-office` 一致（`packages/skill/skill-office/src/index.ts`：`inject = ['skills']`，`ctx.skills.registerProvider(() => provider)`）。dsh 的 skill 查找按 `cwd` 区分（`SkillLookupOptions.cwd`），据此区分协调者与 worker：

```
apply(ctx)                                  inject: ['subagents', 'skills']
 ① ctx.skills.registerProvider(control => { 保存 control; return provider })
 ② WorkerEnvRegistry.register / dispose → control.invalidate()
 ③ provider.list({ cwd })
     ├ cwd 属于存活的 worker checkout（workerEnvs.ownsCheckout）
     │    → { candidates: [auto-research-worker, 已启用插件的 worker skill], complete: false }
     └ 否则 → [auto-research, 已启用插件的协调者 skill]
 ④ provider.get(candidate) → 读取包内 SKILL.md
```

dsh 的 skill 注册表会缓存完整的目录观测，缓存键按 scope 链计算，文档没有说明是否包含 `cwd`。provider 的结果取决于 `cwd` 和当前存活的 worker，因此：
- worker 注册与注销时都调用 `control.invalidate()`（②）；
- 注册表的目录缓存键是 `(cwd, scope 链, revision)`（§9 第 6 项已核实），worker 注册与释放时调用 `invalidate()` 使 revision 加一，所以 worker 列表直接返回数组，不需要 `complete: false`。

核心与 colab 插件的 `inject` 中删除 `systemPrompt`。`skills` 是必需依赖，profile 中必须启用 `dsh-skill` 与 `dsh-tool-skill`，否则协调者没有加载 skill 的途径；README 的安装说明列出这两个前提。`start()` 找不到计划时，错误信息提示先加载 skill `auto-research`，并附包内 `skills/auto-research/SKILL.md` 的绝对路径。

### 3.4 worker：写入分支 checkout

claude-code、codex 等外部 CLI worker 看不到 dsh 的 `ctx.skills`，所以 worker skill 同时写进分支 checkout，并在提示词里给出绝对路径兜底。

```
Runner.branch
 ① fork 或 resume → state.path = checkout
 ② materializeWorkerFiles(checkout)
     ├ .auto-research-methods/BRANCH.json       本分支的动态参数
     ├ .auto-research-methods/WORKER.json       递归防护标记（§6.1）
     ├ .claude/skills/<skill>/SKILL.md          供 claude-code
     └ .agents/skills/<skill>/SKILL.md          供 codex，以及 dsh 的项目级发现
 ③ prelaunchInventory（暂存模式）
 ④ startActivation，提示词 = 任务正文 + 指引行
 ⑤ worker 结束 → reconcile
 ⑥ removeWorkerFiles(checkout)                  只删除 ② 写入的路径与 HANDOFF.md；目录变空时一并删除
 ⑦ evaluate → 协议校验 → commit
```

**提示词**保留任务正文：`objective` 与 `worker_prompt` 是任务本身，worker 不打开任何文件也必须看到。其余全部移入 skill 与 `BRANCH.json`。指引行固定为：

```
先加载 skill `auto-research-worker`；无法加载时读取 <包内绝对路径>/skills/auto-research-worker/SKILL.md。本分支参数见 .auto-research-methods/BRANCH.json。
```

**`BRANCH.json`**：

```json
{
  "schema": 1,
  "run_id": "…",
  "branch_id": "round-1-explore-2",
  "phase": "explore",
  "parent": "initial",
  "checkout": "/abs/host/checkout",
  "layerfs_branch": "ar-…",
  "sandbox_path": "/workspaces/3",
  "deadline_unix": 1793612345,
  "provider_seconds": 1740,
  "evaluation_reserve_seconds": 60,
  "share_target_unix": null,
  "rsi_top": { "portfolio_size": 4, "metric_view": { "definitions": [], "diagnostics": [], "rows": [] } },
  "cooperation": null,
  "handoff": { "from": "round-1-explore-1", "path": ".auto-research-methods/HANDOFF.md" },
  "executor": "local",
  "environment": ["DSH_AUTO_RESEARCH_CHECKOUT", "…"]
}
```

`cooperation` 非空时包含 `index`、`count`、`peer_evidence: { path, sha256, peer_ids }`、`shared_context`。字段与现有 `LAUNCH.json` 一一对应，`LAUNCH.json` 继续作为 runner 侧的记录保留。

**清单排除**：`OMIT`（`layerfs-workspace.ts:44`）新增 `.agents`。`.claude` 与 `.auto-research-methods` 已在其中。写入的文件因此不进清单、不参与评估、不被共享。

**为什么要在 ⑥ 删除**：LayerFS 的 `workspace.commit(ws, message?, force?)` 不支持排除路径（已核对 `layerfs/sdk/js/src/workspace/commit.js`）。非暂存挂载提交时会带上工作区内所有文件，所以 runner 必须在提交前删除自己写入的文件。暂存模式按清单 diff 发布，本来就不含这些路径，删除只是保持一致。仓库自带的 `.claude/`、`.agents/` 内容不受影响，因为只删除 ② 写入的具体路径。

协作 epoch 复用同一个 checkout，每次 `branch()` 调用都重新执行 ② 与 ⑥。

## 4. 插件分层（D7、D8、D9）

### 4.1 两条接缝

| 接缝 | 职责 | 实现 |
|---|---|---|
| `WorkspaceBackend` | 分支放在哪里：baseline / fork / adopt / reconcile / commit / release / 清单 / 容量估算 | `layerfs`（主力）、`snapshot`（回退） |
| `ExecutorBackend` | 计算在哪里跑：冻结评估器的执行，worker 的远端执行入口 | `local`（默认）、`colab`；以后可加 ssh、daytona |

接口定义放在 `dsh-auto-research/api`：

```ts
export interface WorkspaceBackend {
  readonly name: string
  baseline(source: string, id: string): Promise<WorkspaceState>
  fork(parent: WorkspaceState, id: string): Promise<WorkspaceState>
  adopt?(ref: string, id: string): Promise<WorkspaceState>
  reconcile?(state: WorkspaceState): Promise<{ outcome: ReconcileOutcome; conflicts: string[] }>
  commit(state: WorkspaceState, options: { message: string }): Promise<void>
  release(state: WorkspaceState, options: { discard: boolean }): Promise<void>
  estimateForkBytes(parent: WorkspaceState, count: number): Promise<number>
  retainCompletedState(row: TrajectoryRow): Promise<string>
  restoreCompletedState(checkpoint: string, failedRow: TrajectoryRow): Promise<TrajectoryRow>
  close?(): Promise<void>
}

export type ReconcileOutcome = 'unchanged' | 'host' | 'folded' | 'conflict'

// 核心只调用 evaluate；health / exec 是 colab 自己 CLI 的方法，不进接口
export interface ExecutorBackend {
  readonly name: string
  evaluate(request: FrozenEvaluationRequest): Promise<EvaluatorProcessResult>
}

export interface BackendFactory<T> {
  readonly name: string
  readonly priority: number
  create(options: BackendCreateOptions): Promise<T | null>
}
```

`FrozenEvaluationRequest` 包含冻结副本路径、其 SHA-256、argv、超时与工作区路径。`FrozenEvaluator` 保留本地职责：冻结、评估前后校验副本哈希、评估前后比较工作区清单、解析并校验输出。只有"执行评估器进程"这一步交给 `ExecutorBackend.evaluate`。计划字段 `evaluator_interpreter` 保留，作为 `local` 执行后端选择解释器的方式；被取代的只是把它指向 Colab CLI 的用法。

### 4.2 注册表与选择

两个注册表是普通类，由核心插件以 `ctx.provide(name, registry)` 提供；`ctx.provide` 返回的释放函数随核心 fiber 卸载执行。包没有 cordis 依赖，所以不继承 `Service`，也不写 `declare module '@deepseek-ai/cordis'`（无法解析的模块不能扩充，TS2664），服务字段声明在本包的 `PluginContext` 中：

| 服务 | ctx 键 | 方法 |
|---|---|---|
| `ResearchWorkspaceRegistry` | `ctx.researchWorkspace` | `register(factory) → dispose`、`list()` |
| `ResearchExecutorRegistry` | `ctx.researchExecutor` | `register(factory) → dispose`、`list()` |

选择：

```
选择工作区后端
 ① config.workspaceBackend 或 plan.options.workspaceBackend 为具体名称 → 只尝试该工厂，返回 null 即报错
 ② 为 'auto' → 按 priority 从高到低调用 create，取第一个非 null
 ③ 全部为 null → 报错，列出已注册的工厂；核心不再内置兜底实现
执行后端同理，键为 executor
```

优先级：`layerfs` 100、`snapshot` 0；`colab` 100（未配置 endpoint 时 `create` 返回 null）、`local` 0。

`config.layerfs: false` 这一公开的退出开关（`provider.ts:280-283`）保持有效：`layerfs` 工厂的 `create` 在该值下返回 null，`auto` 选择随之落到 `snapshot`。

现有写法删除：`AutoResearchServiceImpl` 预置工厂（`provider.ts:759`）、`index.ts:252-258` 中的 `ctx.provide` 与直接调用 `layerfsWorkspacePlugin.apply(ctx)`、`createWorkspaceManager` 内的默认工厂与 `SnapshotBackend` 兜底（`layerfs-workspace.ts:2108`）。

### 4.3 包结构

同一个 npm 包，多个子路径入口；每个入口是一个 Cordis 插件：

| 子路径 | Cordis 名称 | inject |
|---|---|---|
| `dsh-auto-research` | `dsh-auto-research` | `subagents`、`skills` |
| `dsh-auto-research/layerfs` | `dsh-auto-research-layerfs` | `researchWorkspace`（有 LayerFS skill 时再加 `skills`） |
| `dsh-auto-research/snapshot` | `dsh-auto-research-snapshot` | `researchWorkspace` |
| `dsh-auto-research/local` | `dsh-auto-research-local` | `researchExecutor`，可选 `subprocess` |
| `dsh-auto-research/colab` | `dsh-auto-research-colab` | `researchExecutor`、`skills`，可选 `shellEnv` |
| `dsh-auto-research/api` | — | 只导出类型与共享工具，不是插件 |

核心入口的 `inject` 不含两个注册表：它们由核心自己提供，声明为依赖会让插件永远等不到。挂载顺序：

```
dsh-auto-research.apply(ctx)                    inject: ['subagents', 'skills']
 ① ctx.plugin(ResearchWorkspaceRegistry)        提供 ctx.researchWorkspace
 ② ctx.plugin(ResearchExecutorRegistry)         提供 ctx.researchExecutor
 ③ ctx.inject(['researchWorkspace', 'researchExecutor'], child => {
      构造 AutoResearchProvider；ctx.subagents.registerProvider；注册 skill provider
    })
```

后端插件各自 `inject` 对应的注册表，在 ① ② 完成后由 Cordis 激活并注册工厂。

### 5.2 暂存模式单写入方（D11）

暂存模式下同一分支有两个可写视图：宿主暂存副本与 Sandbox 的 `/workspaces/<n>`。现状 `reconcile`（`layerfs-workspace.ts:1227`）在宿主副本有变化时直接返回，Sandbox overlay 的改动被静默丢弃。

宿主暂存副本是权威写入方，Sandbox 只用于执行。`reconcile` 返回 `ReconcileOutcome`：

| 宿主有变化 | Sandbox overlay 有变化 | 结果 | 处理 |
|---|---|---|---|
| 否 | 否 | `unchanged` | 无 |
| 否 | 是 | `folded` | 提交 overlay，合并回宿主副本（现行行为） |
| 是 | 否 | `host` | 由 `commit` 发布宿主副本（现行行为） |
| 是 | 是 | `conflict` | 见下方步骤 |

`fs.apply` 不能用来发现冲突：它的私有 Workspace 在调用时绑定，Sandbox 提交之后再调用，看到的已是新 head，写入是整文件覆盖，不会报告 `Conflict`（SDK README：只有绑定之后又有其他发布时才合并并报告）。冲突路径在本地计算：

```
Runner.branch → manager.reconcile(state)
 ① hostChanged    = changedPaths(prelaunchInventory, inventory(宿主副本))
 ② sandboxChanges：overlay 脏 → workspace.commit(sandbox 挂载)，Sandbox 改动进入分支历史；remount
                   物化分支 → changedPaths(stagingInventory, 分支清单)（符号链接与无法读取的二进制不计）
 ③ 两边都变 → { outcome: 'conflict', conflicts: ① ∩ ② }
 ④ 行判为 invalid，evaluation.reason = workspace conflict: host and sandbox both modified: <路径>，不运行评估器
 ⑤ 行作为 rejected 提交：syncStaging 用 fs.apply 发布宿主 diff
```

①② 无论宿主是否改动都执行，Sandbox 改动先提交，不会丢失；Sandbox 提交被拒绝时直接抛错，不 remount（remount 以 discard 卸载，会丢掉未提交的 overlay）。`materializeBranch` 在 client 缺少 `fs.list`/`fs.read` 时直接报错（PR6，原为警告后返回空列表），否则空清单会被当作分支删除了全部文件。两边的改动都留在分支历史里；交集为空也判为 invalid，因为被评估的宿主副本不等于分支状态。

非暂存挂载只有一个视图，`reconcile` 恒为 `unchanged`。规则只有三句，写入 worker skill 的 Rules，不单独建 `auto-research-layerfs` skill。

## 7. 删减过度防御（D13）

### 7.1 原则

校验只放在不可信输入上。按来源划分：

| 来源 | 是否可信 | 处理 |
|---|---|---|
| 用户、协调者会话 | 可信 | 不设防 |
| dsh 宿主接口 | 可信，有类型 | 在 `inject` 中声明后直接调用；不探测形状、不做属性兜底、不包空 `catch` |

- `evidence` 必须是被评估工作区内的普通文件。
- 基线评估不通过时不启动任何 worker。
- 不修改原始 checkout；`LATEST.json` 的 `original_manifest` 比对；`leader_workspace` 必须位于 `runs/` 下。
- `PORTFOLIO.json`、`SHARED_CHECKPOINT.json`、`PEER-REVIEW.json` 的格式校验，以及共享检查点的路径与凭据内容检查。
